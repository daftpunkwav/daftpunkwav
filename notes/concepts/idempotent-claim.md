# 幂等认领

> 多方同时抢一个任务时，认领这一步必须能重复执行而不产生副作用。

## 判断

Agent 场景下，重复执行不是异常，而是常态：网络超时重试、模型换了一条路、用户把任务又点了一次。系统要假设同一个动作会发生两次。

如果一个动作是认领任务并开始改文件，那它必须满足：

- **认领是原子的**：要么任务归我，要么不归我，不能两个执行者同时认为自己拿到了。
- **认领是幂等的**：重复认领不会造成重复执行、重复扣费、重复写盘。
- **认领结果可查询**：执行者能问这个任务现在归谁，而不是靠猜。

## 实现上的三种做法

| 做法 | 原理 | 适用 |
| :--- | :--- | :--- |
| 唯一键 + 数据库约束 | `UPDATE ... WHERE id=? AND status='pending'`，看影响行数 | 有关系库，最简单可靠 |
| 带租约的锁 | `SET key owner EX 30`，过期自动释放 | Redis 之类，支持租户抢占 |
| 单写入者 + 队列 | 认领者只负责投递，不直接改状态 | 想把抢任务和干活解耦 |

## 常见坑

- **用先查再改代替原子认领**：`SELECT` 之后 `UPDATE` 之间有窗口期，两个执行者会同时通过检查。
- **锁没有过期时间**：执行者崩溃后任务永远卡住。锁必须带 TTL。
- **认领成功但后续失败没有补偿**：认领本身幂等不等于整个动作幂等。真正要保证的是重复执行的结果和执行一次相同。
- **把幂等交给调用方**：让 Agent 自己记得我刚才做过了是不可靠的，幂等要落在服务端。

## 落到我自己的项目

- [wave-code](https://github.com/daftpunkwav/wave-code)：长任务需要被唯一认领，断点续跑时不会出现两个执行者同时改同一份工作区。
- [breakwater](https://github.com/daftpunkwav/breakwater)：网关侧对同一请求重试、故障切换时的计数与计费要按同一笔业务而不是同一次 HTTP 调用来算。
