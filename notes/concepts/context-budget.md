# 上下文预算

> 上下文不是越多越好，而是刚好够做下一步。

## 判断

Agent 的每一个 token 都要钱，也都要时间。更重要的是，上下文越长，模型越容易在噪声里丢掉重点。

我的取舍是：**上下文按下一步要做什么来裁，而不是按历史有多长来堆**。具体来说：

- **给任务而不是给全记录**：只喂当前这一步需要的文件片段、相关符号、最近一次失败的输出。
- **给结构而不是给原始日志**：日志是原料，结论才是上下文。原始日志留在系统里，需要时再查。
- **给可定位的坐标**：告诉模型看 src/foo/bar.rs 的 40-80 行，比把整个文件贴进去更省。
- **给稳定的事实，丢掉过程噪声**：改了三次失败的方案，通常不用全喂，只留这条路走不通这个结论。

## 裁剪手段

| 手段 | 说明 | 注意 |
| :--- | :--- | :--- |
| 结构化抽取 | 把 DOM / AST 抽成骨架再送模型 | 抽得太狠会丢关键节点，需要保留文本锚点 |
| 分片 + 检索 | 按相关性取片段 | 检索不到时要有兜底，不能空着送 |
| 摘要替代原文 | 用结论替代长过程 | 摘要本身会失真，关键约束要保留原文 |
| 硬预算 | 每次调用设 token 上限 | 超预算要显式报错，不要静默截断 |

## 常见坑

- **静默截断**：上下文超了直接砍尾巴，模型会在信息缺失的情况下编造。应该显式告诉模型这里被省略了什么。
- **保留全部失败尝试**：上下文里塞满走不通的路，模型容易重走老路。
- **把检索结果当事实**：检索出来的是候选，不是结论，要标注来源。
- **只按字符数裁**：中文和代码的 token 密度差很多，预算要按 token 算。
