# 流式优先

> 对话式界面里，开始说比说得全重要。

## 判断

Agent 的等待时间比普通接口长一个量级：如果一次回答要 40 秒，用户看到转圈就会以为卡死。所以**第一句话应该尽早到达**，剩下的内容增量补上。

这不只是体验问题，它还改变了系统的失败模式：

- 流式下，用户 2 秒就能看到进展，10 秒不回复也会知道系统在跑。
- 非流式下，一次超时要等到底才知道，中途无法降级、无法部分展示。
- 流式让先给结论，再补细节成为可能：Agent 可以先输出计划或骨架，边执行边补充。

## 协议怎么选

| 方案 | 特点 | 适用 |
| :--- | :--- | :--- |
| SSE（Server-Sent Events） | 单向服务端推送，基于 HTTP，浏览器原生支持，断线重连语义简单 | 大多数服务端单向推事件的场景，够用 |
| WebSocket | 全双工，连接常驻，需要自己处理心跳、重连、鉴权刷新 | 需要客户端频繁上行、或同一通道要跑控制指令 |
| HTTP 分块 / 长轮询 | 无新协议，兼容性最好 | 极简场景或老客户端 |

我的默认选择是 **SSE**：Agent 场景里绝大多数时候是服务端推、客户端看，SSE 用最少的机制覆盖了大部分需求。只有在同一个连接上要同时下发任务、控制流、取消这类需求出现时，才值得上 WebSocket 的复杂度。

## 常见坑

- **用 SSE 却每条事件都 flush 一次**：几百条事件会把延迟和 CPU 吃掉。要合并高频事件（token 级流式要做节流与缓冲）。
- **没有事件类型**：客户端只能靠字符串猜语义。应给每条事件定义类型（`token` / `tool_call` / `done` / `error`），前端按类型渲染。
- **错误发生在流开始之后**：HTTP 状态码已经发出去了，只能通过流内的 error 事件表达。前端要处理流中途失败，而不是只处理非 2xx。
- **断线没有续传**：重连后从头开始，用户看到重复内容。要么接受重放，要么用事件序号让客户端去重。
