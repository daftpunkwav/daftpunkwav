# 人机同权：UI 与 Agent 共用一套原语

> 用户点的每个按钮，Agent 也要能调用；反过来也一样。

## 判断

很多「AI 工作台」的思路是：给用户一个界面，再给 Agent 一套工具/API，两套东西各自演化。结果是功能重复、行为不一致，而且用户手动做的事 Agent 做不到，Agent 做的事用户看不到。

另一种思路是**同一套原语，两种调用方**：

- 领域操作（建文档、改配置、跑一次查询）定义成一层明确的原语，每条原语有清晰的参数和结果。
- UI 的每个交互最终落到这层原语上。
- Agent 的每个工具也最终落到这层原语上。

这样带来的好处很直接：

- **不需要为 Agent 单独写一套逻辑**，功能只需要实现一次。
- **行为一致**：人做和 AI 做走的是同一条路径，权限、校验、副作用都在一处。
- **可观测**：原语层是天然的埋点位置，两种调用方共享同一套日志和用量统计。

## 关键设计点

1. **原语要正交且可组合**：原语之间不要互相嵌套太深，否则 Agent 组合出来的调用链会很难推理。
2. **原语要够细但不是接口碎片**：粒度太细则调用次数爆炸，太粗则失去控制力。
3. **原语层不能有「只有 UI 能做」的旁路**：一旦有旁路，两种调用方就开始分叉。
4. **Agent 调用的原语要有副作用等级标注**：哪些只读、哪些会改状态，交给上层决定要不要人确认。

## 常见坑

- **给 Agent 开了后门接口**：为了「让 Agent 好用」，额外开了内部接口，绕过了 UI 的约束。分叉从这里开始。
- **原语层被 UI 逻辑污染**：原语里出现「如果是某个页面触发的……」这种判断，Agent 路径就会走偏。
- **只做了读操作的对齐**：写操作两边语义不一致，Agent 做出来的东西用户看不懂。
- **原语的错误信息面向人写**：Agent 需要的是「怎么改」，人需要的是「发生了什么」，两种文案要分别设计。
