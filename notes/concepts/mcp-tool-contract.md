# MCP 作为工具契约

> 把工具怎么被调用从模型的自由发挥，变成一份可校验的契约。

## 判断

工具调用的难点不在于怎么执行，而在于怎么让模型稳定地用对。参数靠自然语言描述时，模型会漏参、串参、把字符串当枚举用。契约的作用就是把调用的形状固定下来。

MCP（Model Context Protocol）做的是这件事：工具用结构化 schema 描述输入输出，客户端负责发现和调用，服务端负责实现。**它不是让 Agent 更聪明，而是让工具怎么被用这件事有确定的答案。**

我认为 MCP 的真正价值在于三点：

1. **一次实现，多个客户端可用**。同一个工具服务不必为每个 Agent 客户端重写一遍接入。
2. **契约可以被校验**。schema 在服务端可以真的做入参校验，错误能明确告诉模型你少填了哪个字段。
3. **工具边界清晰**。工具列表是显式的，这比让 Agent 去猜有哪些命令可以跑要可控得多。

## 常见坑

- **把 MCP 当成万能胶**：它解决的是工具接入的标准化，不解决权限、审计、多租户，这些仍然要在服务端自己做。
- **工具切得太碎**：一个工具只做一步，模型要串很多次调用，每次都有出错机会。粒度按一次调用完成一个有意义的业务动作来定。
- **工具太多**：几十个语义重叠的工具，模型选错的概率反而上升。宁可合并，也不要堆数量。
- **错误信息写给模型看不懂**：返回一句内部错误，模型只能瞎猜。把哪个参数不合法、允许值是什么写进错误信息里。
- **在工具里塞业务逻辑**：工具层应该是薄的一层，复杂判断放服务端，模型只负责选择。
