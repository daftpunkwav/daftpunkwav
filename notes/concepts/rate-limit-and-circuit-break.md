# 限流与熔断

> 给不稳定的外部依赖加一层缓冲：上游抖动时，别让它把调用方一起带崩。

## 判断

调用大模型 API 和调用普通 HTTP 服务不一样：慢、贵、限流规则不透明、还会随机返回上游错误。所以从第一天起就得把「调用模型」当成对外部不稳定依赖的调用来设计，而不是当成一个函数调用。

两件事要分开做：

- **限流（rate limit）**：限制单位时间内的请求量，主动把流量压在上游承受范围内。目的不是「保护自己」，是「不把上游打挂，也让自己拿到更稳定的成功率」。
- **熔断 / 故障转移（circuit breaker & failover）**：上游明确失败或明显变慢时，暂时不再打它，直接切到备用通道。目的是**止损**，把失败变成可预期的降级而不是无限等待。

## 算法上怎么选

| 算法 | 特点 | 适用 |
| :--- | :--- | :--- |
| 固定窗口计数器 | 实现最简单，窗口边界会出现双倍突发 | 内部服务、要求不高 |
| 滑动窗口日志 | 精确，内存随请求量增长 | 限流要求严格、实例数少 |
| 令牌桶 | 允许一定突发，速率平滑 | 大多数 LLM 网关场景 |
| 漏桶 | 输出绝对平滑，不允许突发 | 下游处理能力固定的场景 |

我的选择是令牌桶：既要限制平均速率，又允许短时突发（工具调用常常是连着发的），而且参数好解释——「每秒 N 个令牌，桶容量 M」。

熔断这边比算法更重要的是**状态机**：closed（正常）→ open（直接失败/切换）→ half-open（放少量探针）。探针成功就回到 closed，失败就退回 open。**关键是探针要能真正打到原来失败的那个上游**，否则测的是另一条路的健康度。

## 常见坑

- **没有超时**：限流和熔断都救不了「请求永远不返回」。超时必须先于一切。
- **重试没有退避**：上游只是暂时抖，直接重试会把恢复时间拉长。
- **重试不区分错误类型**：429 和 400 一起重试，400 会被重试到超时。
- **切换时把计费算两遍**：失败的上游可能已经计费了。用量统计要按「业务请求」归集，不能按 HTTP 次数。
- **熔断器状态只在内存**：多实例部署时，每个实例的熔断状态不一致，整体行为不可预测。
